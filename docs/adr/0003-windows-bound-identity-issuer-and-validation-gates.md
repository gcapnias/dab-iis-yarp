# Windows-bound Identity issuer with separate validation gates

The separate .NET 10 issuer uses ASP.NET Core Identity and an EF Core SQL Server application context to own accounts, profiles, roles and permitted claims. The user selected disposable Northwind for the proof, superseding an external identity-schema requirement and an interim SQLite proposal. Northwind is a test environment, not a runtime catalog restriction; the configured SQL Server catalog is reusable. Identity migrations and synthetic test data are isolated from the sample DAB tables.

Bind accounts to the authenticated request's Windows SID on supported Windows IIS or Kestrel/Negotiate hosts. Reading the request token's SID requires a valid queryable token handle, not an AD search account or administrator membership; the worker/process identity must not identify the caller. Local-account SIDs are machine-specific. Missing mappings, absent roles, disabled or locked accounts and conflicting permitted claims fail closed. Account provisioning and role assignment are operator-controlled; there is no automatic Windows-group-to-role assignment or password-login requirement.

Use genuine OpenIddict authorization-code/PKCE and discovery/public-key endpoints rather than advertising fictitious OIDC capabilities in a minimal key document. Keep Windows authentication on caller/session and authorization paths while allowing the public metadata and protocol endpoints required by OIDC. Access credentials carry intended persisted profile/role claims with scope-aware destinations. Refresh credentials are persisted and rotated; replay revokes the affected family, account/security-stamp changes prevent renewal, and cleanup preserves replay evidence until the relevant credential expires. Clearing cookies or revoking refresh does not revoke an already-issued stateless access JWT before its expiry.

The browser cookie session is distinct from Windows Authentication caching. Access and refresh cookies have explicit lifetimes and stable issuance/deletion paths; a root issuer uses an explicit `/` path so rotation replaces the same cookie instead of creating a second path-scoped cookie. Private test signing/encryption keys are retained inside the repository's gitignored `.scratch/identity-issuer/keys/` directory and are excluded from tracked and published artifacts.

Complete local implementation, local proofs, reviews and runbooks before environment evaluation. The browser investigation [Investigate Playwright OIDC callback navigation and missing browser result](https://github.com/gcapnias/dab-iis-yarp/issues/13) and [Prove the Windows Authentication issuer, Profile and Roles lookup, and JWT cookie contract](https://github.com/gcapnias/dab-iis-yarp/issues/11) are closed with an issuer-side go for the local prototype; the [final implementation report](../../archive/research/identity-issuer/implementation-report.md) supersedes the historical stopped-session handoff. The separate [configuration-driven API proof](https://github.com/gcapnias/dab-iis-yarp/issues/9) is also complete; its anonymous permissions alone do not establish issuer-to-DAB interoperability. [Prove issuer JWT compatibility with embedded DAB](https://github.com/gcapnias/dab-iis-yarp/issues/10#issuecomment-5978002240) is now closed with the real local Windows/database/browser chain and both runbooks verified. [Evaluate the completed issuer and embedded DAB on Windows Server IIS](https://github.com/gcapnias/dab-iis-yarp/issues/12) is the next environment gate. These gates do not change the same-process DAB boundary in ADR-0001 or the framework/package baseline in ADR-0002.

The browser's eligibility to send an issuer access cookie is separate from the API request's origin and from DAB authorization. The proven local topology uses separate HTTPS localhost ports: cookies have no port scope, while browser origins do. Requests are made from the API origin; shared cookie scope does not grant CORS access. The host extracts the cookie before DAB authentication, then checks exact API origin and identity-bound antiforgery for unsafe cookie requests. Tokens created after authentication cannot be validated as an anonymous caller. Requested roles must belong to the validated credential and must also satisfy configured resource permissions. Profile presence is not evidence of an unconfigured profile policy.

No software, IIS features or certificate trust changes are installed on the development workstation. The approved Playwright test context uses `ignoreHTTPSErrors: true` for local/self-signed certificates in both local and server test environments; that browser proof excludes certificate-chain and hostname validation, and does not alter production TLS settings. A local Kestrel browser result is not IIS evidence or production readiness.

After normal server-side discovery retrieval rejected the untrusted localhost certificate, the user approved the existing ASP.NET developer certificate for development/evaluation. Prefer explicit process-scoped trust to a workstation trust-store change: the embedded host permits an opt-in exact certificate pin only in Development and only for the configured HTTPS localhost issuer origin. It still requires the matching currently valid Server Authentication certificate and rejects hostname errors or another origin/port; normal CA-backed validation remains the default. Browser certificate bypass does not establish this backchannel trust. HTTPS endpoint certificates and issuer JWT signing keys serve separate purposes; trusting one does not validate the other. The accepted local exception does not authorize remote issuer trust or establish a server/production TLS contract.

The [live interoperability evidence](../../archive/research/dab-jwt-interoperability/LIVE-PROOF.md) records a scoped local GO, reproducible owned-process/disposable-database cleanup and explicit limits. Real browser logout removes the API credential and subsequent requests are denied; stateless access-token expiry is additionally tested with otherwise valid expired controlled tokens. This proof does not wait for a real browser token to expire, nor establish arbitrary production profile policies, multi-user administration or IIS behavior.
