# Windows-bound Identity issuer with separate validation gates

The separate .NET 10 issuer uses ASP.NET Core Identity and an EF Core SQL Server application context to own accounts, profiles, roles and permitted claims. The user selected disposable Northwind for the initial local proof, superseding an external identity-schema requirement and an interim SQLite proposal. Northwind was a test environment, not a runtime catalog restriction. The subsequent server deployment uses an isolated Identity database while DAB exposes read-only Northwind Products; new-install instructions preserve that separation. Identity migrations must target the explicitly selected Identity catalog, and mutation fixtures stay isolated from Northwind sample data.

Bind accounts to the authenticated request's Windows SID on supported Windows IIS or Kestrel/Negotiate hosts. Reading the request token's SID requires a valid queryable token handle, not an AD search account or administrator membership; the worker/process identity must not identify the caller. Local-account SIDs are machine-specific. Missing mappings, absent roles, disabled or locked accounts and conflicting permitted claims fail closed. Account provisioning and role assignment are operator-controlled; there is no automatic Windows-group-to-role assignment or password-login requirement.

Use genuine OpenIddict authorization-code/PKCE and discovery/public-key endpoints rather than advertising fictitious OIDC capabilities in a minimal key document. Keep Windows authentication on caller/session and authorization paths while allowing the public metadata and protocol endpoints required by OIDC. Access credentials carry intended persisted profile/role claims with scope-aware destinations. Refresh credentials are persisted and rotated; replay revokes the affected family, account/security-stamp changes prevent renewal, and cleanup preserves replay evidence until the relevant credential expires. Clearing cookies or revoking refresh does not revoke an already-issued stateless access JWT before its expiry.

The browser cookie session is distinct from Windows Authentication caching. Access and refresh cookies have explicit lifetimes and stable issuance/deletion paths; a root issuer uses an explicit `/` path so rotation replaces the same cookie instead of creating a second path-scoped cookie. Local test signing/encryption keys remain in protected, gitignored `.scratch/identity-issuer/keys/`; deployed keys are provisioned separately in a protected server directory outside published application files. Neither belongs in tracked source or binary publish artifacts. Scratch retention does not establish backup or key recovery.

Complete local implementation, local proofs, reviews and runbooks before environment evaluation. The browser investigation [Investigate Playwright OIDC callback navigation and missing browser result](https://github.com/gcapnias/dab-iis-yarp/issues/13) and [Prove the Windows Authentication issuer, Profile and Roles lookup, and JWT cookie contract](https://github.com/gcapnias/dab-iis-yarp/issues/11) are closed with an issuer-side go for the local prototype; the [final implementation report](../../archive/research/identity-issuer/implementation-report.md) supersedes the historical stopped-session handoff. The separate [configuration-driven API proof](https://github.com/gcapnias/dab-iis-yarp/issues/9) is also complete; its anonymous permissions alone do not establish issuer-to-DAB interoperability. [Prove issuer JWT compatibility with embedded DAB](https://github.com/gcapnias/dab-iis-yarp/issues/10#issuecomment-5978002240) is now closed with the real local Windows/database/browser chain and both runbooks verified. [Evaluate the completed issuer and embedded DAB on Windows Server IIS](https://github.com/gcapnias/dab-iis-yarp/issues/12) is also complete, with the accepted server refinement below recording its separate evidence and scope. These gates do not change the same-process DAB boundary in ADR-0001 or the framework/package baseline in ADR-0002.

The browser's eligibility to send an issuer access cookie is separate from the API request's origin and from DAB authorization. The proven local topology uses separate HTTPS localhost ports: cookies have no port scope, while browser origins do. Requests are made from the API origin; shared cookie scope does not grant CORS access. The host extracts the cookie before DAB authentication, then checks exact API origin and identity-bound antiforgery for unsafe cookie requests. Tokens created after authentication cannot be validated as an anonymous caller. Requested roles must belong to the validated credential and must also satisfy configured resource permissions. Profile presence is not evidence of an unconfigured profile policy.

No software, IIS features or certificate trust changes were installed on the development workstation during the evaluated proofs; existing tools ran browser checks there. The user separately authorized server preparation and missing-component installation. The approved Playwright test context uses `ignoreHTTPSErrors: true` for local/self-signed certificates in local and server tests; this excludes browser chain/hostname validation and does not alter application or production TLS settings. A local Kestrel browser result is not IIS evidence or production readiness.

After normal server-side discovery retrieval rejected the untrusted localhost certificate, the user approved the existing ASP.NET developer certificate for development/evaluation. Prefer explicit process-scoped trust to a workstation trust-store change: the embedded host permits an opt-in exact certificate pin only in Development and only for the configured HTTPS localhost issuer origin. It still requires the matching currently valid Server Authentication certificate and rejects hostname errors or another origin/port; normal CA-backed validation remains the default. Browser certificate bypass does not establish this backchannel trust. HTTPS endpoint certificates and issuer JWT signing keys serve separate purposes; trusting one does not validate the other. The local exception does not transfer to remote issuers; the separately authorized test-server trust decision is recorded below. Neither establishes production TLS policy.

The [live interoperability evidence](../../archive/research/dab-jwt-interoperability/LIVE-PROOF.md) records a scoped local GO, reproducible owned-process/disposable-database cleanup and explicit limits. Real browser logout removes the API credential and subsequent requests are denied; stateless access-token expiry is additionally tested with otherwise valid expired controlled tokens. This proof does not wait for a real browser token to expire, nor establish arbitrary production profile policies, multi-user administration or IIS behavior.

See the [issuer runbook](../runbooks/windows-authentication-jwt-issuer.md), [Windows-principal research](../../archive/research/identity-issuer/windows-principal-identity-binding.md), and [session handoff](../../archive/research/identity-issuer/session-handoff-2026-10-02.md) for contracts, evidence and remaining work.

## Accepted server refinement, 2026-10-04

The [Windows Server 2025/IIS evaluation](../../archive/research/windows-server-iis/EVALUATION.md) completed with a scoped environment GO. The root issuer and `/dab` API share one HTTPS website/origin but use separate ApplicationPoolIdentity workers without custom pool credentials. The installation administrator, non-administrator Windows proof caller, worker accounts, and SQL logins have distinct responsibilities. Provisioning a caller on another server yields a new local SID requiring its own issuer mapping; cached Windows authentication or OS group membership does not supply persisted issuer roles.

IIS enables Anonymous and Windows Authentication at the issuer root so public discovery/JWKS remain reachable while the application requires the caller on protected routes. Windows Authentication is explicitly disabled for the API, which uses DAB's Custom JWT provider. Anonymous IIS handling does not make configured API resources publicly accessible. Shared origin/cookie scope does not collapse either application boundary or bypass configured resource permissions and identity-bound mutation protection.

The user approved a hostname self-signed HTTPS certificate with its public certificate trusted on the **test server**, allowing normal DAB discovery/JWKS backchannel validation. A localhost certificate/pin is insufficient for that remote hostname. Workstation browser bypass remained a separate client setting with no trust-store changes. HTTPS private keys, issuer signing/encryption keys, Windows credentials and SQL credentials are distinct materials with different readers; recovering a matching signing key is different from rotating it.

The user explicitly approved SQL credential storage in the protected server DAB configuration, readable only by SYSTEM, administrators and the API pool. Issuer configuration/keys are restricted to SYSTEM, administrators and the issuer pool. The API's parent configuration-discovery access is directory-only plus the non-secret parent `web.config`, not recursive issuer-secret access. The reproduction procedure protects and asserts server ACLs **before** private-key transfer and verifies secret-file grants after configuration. This is the accepted test-server mechanism, not a production secret-management decision.

Operator migrations, account/client provisioning and startup must use the same identified Identity catalog. Explicit process configuration avoids the local convenience launcher's `.env` precedence accidentally selecting another database. Existing-caller credential re-export and matching test-key retrieval support retained-server verification; they do not authorize recreating accounts/databases or generating replacement keys on that server. The [reviewed clean-install guide](../runbooks/windows-server-2025-clean-install.md) and [retained-state runbook](../runbooks/windows-server-iis-evaluation.md) distinguish those workflows.

The four runbooks passed follow-up advisor reviews and were approved by the user before publication through `60eda24`. Their review and successful existing-server checks do not establish installation on a second empty server. This completes the environment gate while preserving ADR-0001's same-process boundary and ADR-0002's baseline. Required lifecycle, observability, deployment and recovery guarantees remain the human decision in [ticket #14](https://github.com/gcapnias/dab-iis-yarp/issues/14); production identity operations, key/secret policy and rollout remain outside this evaluation.
