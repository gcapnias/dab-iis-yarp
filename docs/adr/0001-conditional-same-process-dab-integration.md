# Conditional same-process DAB integration

Proceed with specifying an ASP.NET Core application that hosts the real DAB Core engine in the same process through application-owned bootstrap and HTTP adapters. The user accepts ownership of this integration layer, supplemental dependency pins, and upgrade validation to preserve the required single-application access boundary despite the absence of an established upstream-supported embedding contract.

The application must expose all REST and GraphQL endpoints, operations, and permissions enabled by DAB configuration. Configuration changes may require an application restart but must not require recompilation. MCP is optional. The target framework and package policy are recorded in [ADR-0002](0002-net10-and-proven-dab-core-baseline.md).

This is a conditional go for specification, not production readiness. The original Core 2.0.12 spike demonstrated a fixed anonymous Products read adapter on .NET 8 and .NET 10. The subsequent [configuration-driven API proof](https://github.com/gcapnias/dab-iis-yarp/issues/9#issuecomment-5961615935), completed on 2026-10-03, demonstrates same-process REST and GraphQL operations and configured anonymous permissions, plus entity and endpoint changes after restarting the unchanged binary. Security, lifecycle, deployment under IIS, and the final acceptance matrix remain subsequent planning and validation gates.

JWT bearer authentication and DAB permission enforcement are required for REST and GraphQL. Tokens are issued by another application and validated using DAB's Custom provider; the DAB application does not issue tokens. The embedded host must validate tokens and apply the configured DAB roles and permissions; the anonymous spike is not evidence of that integration. The security proof must include valid permitted requests, invalid or expired tokens, authenticated callers lacking permission, unauthorized role selection, and issuer/audience validation. The concrete issuer URL, audience, signing-key lifecycle, and profile claims remain to be specified; compatibility of the agreed discovery and roles contract must be demonstrated. DAB documents JWT support through Microsoft Entra ID and its Custom provider: [security overview](https://learn.microsoft.com/azure/data-api-builder/concept/security/overview) and [custom JWT authentication](https://learn.microsoft.com/azure/data-api-builder/concept/security/authenticate-custom).

Revisit the decision if required REST or GraphQL behavior cannot be exposed from configuration without rebuilding, the agreed issuer JWTs cannot be validated and authorized correctly by DAB, or the integration cannot be maintained across the selected package upgrades. A separate DAB process or application would change the agreed boundary and requires a new user decision.

The external identity issuer is an ASP.NET Core .NET 10 C# application. It authenticates users through Windows Authentication, retrieves profiles and roles from an existing database, and issues JWTs for the DAB application. Token issuance must bind claims to the authenticated Windows identity and database results. The issuer will expose standard OpenID Connect discovery and public signing keys for DAB's Custom provider, and place named roles in the `roles` claim. Profile claims influence authorization only through explicitly configured policies. Production issuer delivery remains outside this planning map.

The original decision scoped the immediate interoperability proof to synthetic profile/role inputs, leaving real Windows Authentication and database lookup outside that focused spike. After advisor review, the user approved an expanded issuer-side proof and revised work order: first research and prototype the real Windows identity-to-database Profile/Roles-to-signed-JWT chain, discovery, and browser cookie delivery; next prove configuration-driven REST/GraphQL access; finally validate the prototypes together. The issuer proof publishes a creation runbook and implementation report, with DAB interoperability explicitly pending. It requires an authorized development Windows Authentication environment and existing-database access; fixture results cannot establish real-chain success.

The embedded DAB application owns the cookie-to-token bridge. The final interoperability proof reuses the issuer prototype, implements that bridge, and verifies real DAB JWT validation, configured permissions, and the browser cookie/CSRF contract through REST and GraphQL. Synthetic inputs remain useful as controlled tests. The issuer runbook initially separates verified issuer steps from proposed DAB integration, then gains verified DAB instructions after interoperability passes.

Preferred work order is expressed by native map child order, not by a technical dependency between the issuer and configuration-driven API proofs. Both can run independently; the final interoperability proof depends on both. See [issuer research and prototype](https://github.com/gcapnias/dab-iis-yarp/issues/11), [configuration-driven API proof](https://github.com/gcapnias/dab-iis-yarp/issues/9), and [JWT/cookie interoperability proof](https://github.com/gcapnias/dab-iis-yarp/issues/10). This revision does not broaden the historical anonymous-read evidence or establish production readiness.

Develop both runnable proof prototypes under `src/` on `develop`: the JWT issuer and the DAB-integrated application. Their purpose is to validate the architecture and provide reproducible evidence for the implementation specification, rather than deliver production applications.

Decision ticket: [Decide whether Core-only same-process DAB is viable](https://github.com/gcapnias/dab-iis-yarp/issues/7). Evidence: [Core hosting research](../../archive/research/dab-core-hosting/README.md).

The issuer persistence, Windows-account binding, genuine OIDC/refresh requirements, and separate local/browser/server validation gates were refined during the issuer implementation. [ADR-0003](0003-windows-bound-identity-issuer-and-validation-gates.md) records the accepted changes, including application-owned Identity persistence in the disposable development database rather than a required external identity schema. The same-process DAB boundary remains unchanged.

## Configuration-driven API evidence, 2026-10-03

The API proof is merged into local `develop` at `ec81bcd` and its decision ticket is closed. The [proof report](../../archive/research/dab-core-hosting/CONFIGURATION-DRIVEN-PROOF.md), [sanitized evidence](../../archive/research/dab-core-hosting/evidence-ticket-9.txt), and [DAB runbook](../runbooks/dab-core-web-application.md) record 62 passing disposable-fixture checks with a zero-warning/error build. The existing issuer suite passed 34 checks. The verifier removed its randomly named database and preserved the original Products-read evidence. Commits remain unpushed at this recording.

Application-owned adapters must preserve the pinned DAB HTTP contract as well as expose configured routes. Review exposed that PUT/PATCH upsert dispatch alone loses update-only semantics: no `If-Match` retains upsert, exact `If-Match: *` selects update-only, and other present values are rejected with HTTP 400. Regression evidence now covers existing-row updates, missing-key rejection without insertion, invalid headers without mutation and default inserts. This is a verified consequence of owning the adapter, not a new integration boundary.

The API proof uses the Unauthenticated provider and controlled anonymous permissions. It demonstrates per-operation REST denial and GraphQL schema omissions, but does not establish validated caller role selection, JWT validation, cookie transport or CSRF protection. An arbitrary role header did not change the effective anonymous role. Neither issuer-side success nor anonymous API success substitutes for the real issuer-to-DAB chain. [Prove issuer JWT compatibility with embedded DAB](https://github.com/gcapnias/dab-iis-yarp/issues/10) reuses both completed prototypes and is the next gate; it must verify the Custom provider, host cookie bridge and configured REST/GraphQL authorization before any security go finding. Database-specific operations outside the demonstrated fixture coverage and IIS remain unproven.
