# Local Windows/database issuer-to-DAB proof

Date: 2026-10-04. Baseline: `9b34d5a` plus the reviewed development-certificate and live-proof changes, .NET 10 and Core 2.0.12.

## Current result

Local browser interoperability passed. The real issuer on `https://localhost:5001` authenticated the current Windows caller, resolved the existing SQL Identity profile and roles, and issued its Secure/HttpOnly/host-only access cookie. Both the PowerShell and isolated Edge checks confirmed session creation; claims were inspected only in memory and only presence booleans were reported. No operator identity/role provisioning or production data change was made.

The embedded API runs separately on `https://localhost:5002` against a disposable `dab_ticket9_<12 hex>` database. Its local ignored configuration maps the existing persisted role(s) to CRUD on `Widget` and read-only access on `RetiredWidget`, using the real issuer and audience. No synthetic issuer or signing key is substituted. The same host-only localhost cookie is eligible for both ports; API browser requests originate from the API origin, so this does not depend on CORS.

The first browser run stopped at API navigation. A separate authenticated HTTP request to `/host` returned HTTP 401 with a bearer challenge. Normal HttpClient retrieval of the real issuer discovery document failed with `AuthenticationException`; `dotnet dev-certs https --check --trust` reported no trusted development certificate. The browser-only `ignoreHTTPSErrors` setting does not control DAB's server-side discovery/JWKS client. These observations do not establish a successful live DAB request.

The user authorized using the local developer certificate for development/evaluation. The API now supports an explicit `DAB_DEVELOPMENT_ISSUER_CERTIFICATE_SHA256` pin only in Development. Its backchannel accepts only the configured HTTPS localhost authority and exact certificate, with valid dates and Server Authentication usage. Hostname errors, other origins/ports, absent/wrong pins and expired certificates are rejected. Normal TLS validation remains the default when the pin is absent; pin use outside Development fails startup. No certificate was installed or trusted in the Windows store. The public leaf inspected during setup must match an already installed ASP.NET development certificate before the harness chooses its pin.

After this change, the isolated browser run passed all 19 checks: real Windows/database session, secure host-only access cookie, persisted profile/role presence, HttpOnly visibility at the API origin, REST and GraphQL fixture reads, missing-CSRF rejection on both transports, successful cookie-authenticated mutations on both transports, configured write denials on the read-only entity, ungranted-role denial on both transports, inserted-row deletion, issuer logout, cookie removal from the API's browser context, and subsequent anonymous REST/GraphQL denial. The controlled regression suite passed 12 tests with zero failures/skips and zero build warnings/errors, including the pin's negative security cases.

The tracked full setup/browser/cleanup command was rerun after advisor feedback strengthened process ownership and failure cleanup; it exited 0 with all 19 checks true, removed its disposable database and left no test listeners. The final independent Standards/Spec review found zero documented violations and zero unresolved spec defects, with one optional duplicated-denial-helper concern. This is a **local interoperability GO** for the documented prototype contract, not IIS or production acceptance.

## Reusable browser check

Run `pwsh -NoProfile -File scripts/test-dab-issuer-live.ps1` from the checkout. It builds the API, starts the existing issuer launcher, identifies its public developer certificate, creates and configures a uniquely named disposable API fixture, runs the browser check and stops the owned processes/removes the fixture in `finally`. Ports 5001/5002 must be free; the script refuses to stop pre-existing listeners. It requires the existing ignored `.env`, issuer keys/development certificate, provisioned Windows/SQL Identity mapping and installed Edge/Playwright CLI. It installs no prerequisites and performs no migrations or identity provisioning. Ignored configuration and logs remain under a unique `.scratch/dab-live-*` path.

For already running applications, `scripts/test-dab-issuer-browser.ps1 -Issuer https://localhost:5001 -Api https://localhost:5002` uses the installed Edge/Playwright CLI in an isolated context. Both origins must be HTTPS localhost roots on separate ports. It reports only check booleans and sanitized failure identifiers; raw tokens, cookies, account/profile values and private keys remain unprinted and untracked.

The browser's approved `ignoreHTTPSErrors` setting and PowerShell's loopback `SkipCertificateCheck` do not prove certificate-chain/hostname validation by those clients. DAB's narrowly pinned server-side backchannel does retain hostname, validity, usage and exact-certificate checks; a publicly/privately trusted CA chain is outside this development proof.

The synthetic suite's invalid-signature/issuer/audience/expiry cases remain complementary controlled evidence. The live run exercises the real persisted role(s) under explicit disposable API permissions; it does not prove arbitrary production profile policies or multiple operator identities. Logout removes the browser credential but does not revoke a previously copied stateless JWT. Access-JWT expiry enforcement is proven by otherwise valid expired synthetic tokens; waiting for a real browser token to expire is outside this run. IIS and Windows Server evaluation remain a separate later gate. Localhost port sharing does not prove a production domain/path topology or CA trust.
