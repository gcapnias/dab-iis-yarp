# Ticket #11 implementation report and coverage matrix

Date: 2026-10-02. Ticket: [Windows Authentication issuer, profile/roles lookup, and JWT cookie contract](https://github.com/gcapnias/dab-iis-yarp/issues/11). This report covers the approved expanded scope: ASP.NET Core Identity, SQL Server persistence, a Windows-authenticated OIDC provider, and a first-party short-lived cookie bridge. It does not claim ticket #10's embedded-DAB interoperability proof.

## Result

Current completion assessment: **issuer-side go for the local prototype**, following the completed browser investigation and merge `6d7fc6c`. The historical validation counts and stopped-work notes below describe earlier revisions; the final completion record at the end supersedes those pending-status statements. DAB interoperability, Windows Server/IIS and production delivery are not established by this result.

The separate .NET 10 issuer now uses ASP.NET Core Identity EF stores and a dedicated SQL Server context, binds authenticated Windows request SIDs to operator-provisioned Identity users, and runs a genuine OpenIddict authorization-code/PKCE flow. OpenIddict publishes complete discovery and JWKS metadata, issues signed ID/access tokens, and persists reference refresh grants. A separate cookie bridge issues an access JWT cookie and rotates persisted opaque refresh cookies under Windows authentication and antiforgery protection.

The authorized disposable Northwind database currently has five migrations applied in schema `IdentityIssuer`. The latest three additive migrations create `OidcRefreshTokenUses`, add each consumed refresh token's expiry, and assign a finite 30-day fallback to orphan markers whose OpenIddict entry is already gone. A read-only SQL check before these additive migrations listed all 13 existing tables under the schema and confirmed the standard Northwind `Categories`, `Customers`, `Orders`, and `Products` tables remained present. The regenerated idempotent SQL artifact has 14 `CREATE TABLE` statements total, zero `DROP` statements, and no Northwind sample-table references; the latest migrations add one table and one column in `IdentityIssuer` and backfill marker expiry there. No Northwind sample rows were changed by the issuer migrations.

## Safe recovery note

During migration authoring, an `ef migrations remove --force --no-build` command ran before the generated source migration had been rebuilt. EF therefore selected the already-applied initial migration and rolled back the `IdentityIssuer` schema and its synthetic Identity rows. No Northwind sample tables or rows were targeted. The schema was recreated by applying the reviewed original and additive migrations; the OIDC client and one new synthetic test identity/role/claim were then provisioned. Current migration state includes all five migrations; the sample-table inventory was confirmed before the last three strictly schema-local migrations. This mistake did not alter source sample data.

While locating the authorized local `.env` key, a text-search command printed its connection-string line into the agent's tool transcript. The credential value is omitted from this report and is not present in tracked artifacts, application logs, or committed output. No credential rotation was requested or performed; the parent was notified. Future checks use in-memory parsing that never outputs the value.

## Limits and delivery boundary

The current real proof uses Kestrel on HTTPS loopback with Windows Negotiate and the current Windows request identity. The harness intentionally bypasses all certificate validation for that loopback development endpoint; it does not establish certificate name or chain trust. IIS hosting, browser cookie behavior across the eventual host names, Windows trust of the local development certificate, and DAB REST/GraphQL consumption/authorization were not tested. The DAB bridge contract is described in the runbook, but its runtime compatibility and permission behavior stay with ticket #10. These are separate from the verified issuer-side chain.

Related durable research already integrated on local `develop`: ASP.NET Identity/.NET 10 at `13bbe1b` and OIDC discovery behavior at `2565aac`. The original user-supplied Identity and Windows-auth artifacts remain unchanged.
